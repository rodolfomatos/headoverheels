# D011 — a tile index and a fraction of a tile are two different values

## What was measured

```
key east: 1.0,1.0 -> 2.87,1.0
```

The party walks on tiles. `gridPosition` returns `position`, a `Vector3` of
doubles. So a single frame moves 0.001 tiles and rounds to the same integer, which
is why the movement tests need sixty frames before they see anything, and why an
assertion of `moved.x > start.x` would pass for a hundredth of a tile of drift just
as readily as for a tile of movement. Every movement test in this project is sixty
times slower than it needs to be and correspondingly less precise than it looks.

## The decision

`gridPosition` is **the tile the party is on**: integral, and what placement, every
movement assertion and every tile lookup uses. `position` keeps the fraction, and
is what the renderer draws with.

Not a preference. The name said one thing and the value was another, and a name
that disagrees with its value is how a test comes to need sixty frames to see a
tile.

## What it costs

Sub-tile positions are wanted for two things: smooth animation, and sliding.
Neither needs the *position* to be fractional. Both need the *rendered* position to
be fractional, and the renderer already reads `position`.

## What this does not do

It does not round the underlying state. `position` stays a `Vector3` of doubles and
still integrates freely; the tile index is a read of it. Nothing is quantised that
was not already quantised for drawing, and no movement becomes steppy.

## The correction

This record first claimed the change made every movement test sixty times faster.
Measured, that is false: at one tile a second a tile takes sixty frames, and the
tests already spent sixty. The claim was arithmetic about types rather than about
this game, and it has been corrected above rather than quietly dropped.
