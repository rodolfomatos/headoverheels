# D006 — the party left every tree

> **Corrected 2026-10-02.** This record said the party was unattached during a
> room change and that no test could reach one. The first half was right and is
> fixed; the second was true only in the strict sense, and it is not why there is
> no test any more. `aes_metrics.py conflict` failed on it when T087 was closed,
> because a ticket recorded as done whose own basis says the work is not
> established is a contradiction, and this was one.
>
> The re-adjudication is D010.

## What was wrong

`_unloadCurrentRoom` removed each character from the very list it was iterating,
which throws `ConcurrentModificationError`, so the room change died there and the
door did nothing. `removeCharacter` also detaches, and the room was the only
parent, so both characters ended up in no tree at all. A `FlameGame` draws no
tree but its own, so on the first door the party was not in another room: it was
gone. Fixed: the party goes to `world` between rooms and is reparented into the
room it stands in, iterating a copy.

## Why there is still no test for it

A room change cannot be driven inside `testWidgets`, and this is a property of
the harness, not of the game. Measured:

- `transitionTo` awaits the new room's tileset decode, which needs the real event
  loop, so it must be started inside `runAsync`.
- `runAsync` denies a second call while the first is pending, so it cannot be the
  thing that drives the change to completion.
- The mount of the room needs `pump`, and every render test in this package
  freezes the engine so two frames differ only by what the test changed — so
  nothing turns until `resumeEngine`.
- `resumeEngine` restarts the game's own `GameLoop` timers, which the test
  binding counts as pending async work. `runAsync` is then refused. An empty
  `runAsync` at the top of the same test body passes, and the identical loop in
  `loadRealGame` passes while the engine is running.

Three mutually exclusive requirements. The combination hangs for minutes and the
runner reports it as a sink error, not as a failure, so a test written against it
looks like a flake.

## What was rejected

Driving `game.update(0)` by hand inside `runAsync`: the lifecycle pass never runs
and the transition never completes (measured, 400 turns). Awaiting the transition
with `withLoop`: deadlock, same cause.

## What is left

Nothing about the party. `room_transition_test.dart` starts a transition without
awaiting it and asserts that both characters are in a tree the game draws at every
step, that nothing throws, that the room changed, and that the party is in the room
afterwards.

Awaiting the *whole* transition is still impossible in a widget test, and the
measurements above still stand. It is simply not the reason there is no test: a
test that watches the invariant during a transition does not need to wait for the
transition to finish.
